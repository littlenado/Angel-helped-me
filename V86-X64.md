# x86-64 (long mode) engine

The page can run 64-bit guests with a second v86 build that includes long mode.

## Files

| File | What it is |
| --- | --- |
| `libv86-x64.js` | `portlandhodl/v86_64` release build, patched by `tools/patch-x64-engine.js` |
| `v86-x64.wasm` | main x86-64 wasm (memory up to 3072 MB) |
| `v86-x64-fallback.wasm` | the fork's fallback wasm build |
| `v86-x64-mem64.wasm` | memory64 build, used above 3072 MB of RAM |
| `libv86.js`, `v86.wasm` | the original 32-bit engine, still the default |

Both engines expose the same `new V86(options)` API. `index.html` keeps the
constructors as `window.V86_32` and `window.V86_64`; the boot code picks one
from the **Processor** selector.

## Updating the engine

1. Download the four release assets from
   `https://github.com/portlandhodl/v86_64/releases/download/latest/`.
2. Copy `libv86.js` to `libv86-x64.js` and the wasm files to the names above.
3. Run `node tools/patch-x64-engine.js`. It applies:
   - `cpu_cap` on the run loop (the CPU execution cap slider),
   - 16 KB written-sector tracking (`cx`/`dirty`) and `get_as_file` for
     file-backed async disks, with disk contents kept out of `get_state`,
   - always-present IDE primary/secondary channels and PCI IDE device,
   - hard disk B support when A is empty,
   - IDENTIFY major-version and multiple-sector fields for Windows storage
     drivers.
4. Run `node tools/build-standalone.js` to refresh `index-standalone.html`.

The patch script is intentionally text-based on the minified build. If the
upstream minifier changes a symbol, it stops with a clear "expected 1 match"
error instead of silently skipping a patch.

## Standalone build

`tools/build-standalone.js` inlines both engines and base64-encodes the
firmware and all wasm files into `window.EMBEDDED`. The
`.github/workflows/standalone.yml` workflow rebuilds the file on every push to
`main`, uploads it as a workflow artifact, and creates or updates the
`standalone` GitHub release.
